## 1. 引言

### 1.1 编写目的

本文明确小信助手智能体的功能需求、非功能需求、接口需求和约束条件，作为系统设计、开发、测试和验收的依据。

### 1.2 适用范围

适用于项目的产品、研发、测试、实施和验收人员。需求覆盖四部分：小信助手桌面客户端、小信助手管理端（含运维人员移动端）、信创垂域大模型能力底座、信创终端适配。

### 1.3 术语

| 术语 | 说明 |
|---|---|
| 信创终端 | 采用国产 CPU（飞腾、鲲鹏、海光、兆芯等）和国产操作系统（银河麒麟、统信 UOS 等）的办公终端 |
| 双轨运行 | 同一使用人同时使用信创终端和原 Windows 终端的过渡期状态 |
| 双系统 | 同一台终端同时安装国产操作系统和 Windows 系统，属于违规情形 |
| 保障中心 / 保障站 | 市级信创保障中心、区县信创保障站，负责终端运维服务 |
| RAG | 检索增强生成：先从知识库检索相关内容，再交给大模型生成回答 |
| 槽位填充 | 对话中识别并持续收集完成某项任务所需的关键参数 |
| LoRA / QLoRA | 参数高效的大模型微调技术 |
| OFD | 我国自主的版式文档格式标准 |

## 2. 项目概述

### 2.1 建设背景

信创终端大规模替代后，终端数量多、型号杂、分布广，用户在使用国产软硬件时遇到的问题多，保障中心的运维压力大。需要一个部署在终端上的智能助手，帮助用户自助解决常见问题、优化终端性能，并让管理部门实时掌握终端的接入、替代、运行和合规情况；同时建设信创垂域大模型能力底座，为问答、知识检索和合同审查等智能服务提供支撑。

### 2.2 建设目标

1. 为终端用户提供一键提速、智能问答、本地知识问答、合同智审、消息接收等桌面服务；
2. 为管理部门提供终端资源、运行情况、监测指标和违规预警的统一管理与可视化；
3. 为保障中心提供来电登记、工单流转、移动处置、案例沉淀的智能运维闭环；
4. 建设可接入多种大模型、可微调、可评估的信创垂域大模型能力底座，以及信创知识库、合同智审和工具插件能力；
5. 完成 4 种国产 CPU、2 种国产操作系统、3 种杀毒软件的适配验证。

### 2.3 用户角色

| 角色 | 使用端 | 主要职责 |
|---|---|---|
| 终端用户 | 桌面客户端 | 使用提速、问答、合同审查、消息、软件中心，发起报修 |
| 系统管理员 | 管理端 | 终端与客户端管理、模型与知识库管理、规则与工具管理、用户与系统设置 |
| 保障中心客服 | 管理端 | 来电登记、工单指派、挂起审核、评价录入、案例查询与维护、消息推送 |
| 运维人员（市保障中心 / 区县保障站 / 纳管厂商） | 移动端 H5 | 工单签收、转派、挂起、信息补充、反馈、补录，上报典型案例 |
| 第三方开发者 | 开放平台 | 开发并接入第三方工具插件 |

### 2.4 系统组成

```
小信助手智能体
├── 桌面客户端：一键提速 · 探针监测 · 悬浮助手 · 智能问答 · 合同智审
├── 管理端：终端资源管理 · 终端运行监测 · 客户端管理 · 消息管理 · 智能运维
│   └── 运维人员移动端：运维工单处置
├── 信创垂域大模型能力底座：模型管理 · 模型优化 · 信创知识库管理 · 合同智审服务 · 工具与插件
└── 信创终端适配：4 种 CPU × 2 种操作系统 × 3 种杀毒软件
```

| 编号 | 功能 | 需求描述 | 验收要点 | 优先级 |

| AI-03 | 模型微调 | 构建信创垂域模型训练流水线；对 2 万+ 信创运维知识和 1000+ 政策知识做数据预处理（格式标准化、质量清洗、标注规范）；建立分层知识体系（运维知识按技术栈、故障类型、解决方案分类，政策知识按法规层级、适用范围、时效性整理）；采用 LoRA、QLoRA 等参数高效微调；构建训练监控，实时跟踪损失函数和收敛情况 | 数据集可上传并自动清洗分类；可选 LoRA / QLoRA；训练过程显示 loss 曲线 | 高 |

#### 3.4.3 信创知识库管理

## 7. 约束与假设

1. 工期：合同签订之日起 9 个月内完成开发并部署上线。
2. 部署环境：服务端部署在 CentOS ARM 服务器；终端多处于内网环境。
3. 大模型：使用公网模型时需服务器可访问对应接口；私有化部署的模型需提供 OpenAI 兼容接口。
4. 真实微调训练需要具备 GPU 的训练环境；无 GPU 时提供训练流程演示。
5. 客户端安装包需在对应 CPU 架构的终端上分别打包。
